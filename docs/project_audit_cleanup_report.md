## 4. CONCURRENCY, INTEGRITY & SECURITY VALIDATION

### 4.1 Concurrency Safety

1. **Simultaneous Check-In Protection:**
   - PostgreSQL unique constraint `uq_employee_attendance_date` on `(employee_id, attendance_date)` guarantees only one check-in can commit.
   - Concurrently racing requests catch `IntegrityError` and cleanly return `HTTP 409 Conflict` (`"Attendance record already exists for this employee today."`).
2. **Simultaneous Check-Out Protection:**
   - Enforces pessimistic row-level locking via `select(AttendanceRecord).where(...).with_for_update()`.
   - Competing requests are serialized; the first commits and the second receives `HTTP 400 Bad Request` (`"Employee has already checked out for today."`), preventing corrupted durations.
3. **Independent Workers:**
   - Concurrently checking-in independent employees process simultaneously without cross-blocking.

### 4.2 Security & Role-Based Access Control

1. **RBAC:** Admin endpoints require `require_admin_user`; employee tokens receive `HTTP 403 Forbidden`.
2. **Data Isolation:** Employee queries to `/api/v1/attendance` are strictly bounded to the authenticated employee's ID.
3. **Deactivated Accounts:** Deactivated accounts receive `HTTP 403 Forbidden: "Employee account has been deactivated. Contact your administrator."`.
4. **Dynamic QR Token Security:** Salted cryptographic tokens with 18-second expiration; expired/tampered tokens receive `HTTP 400 Bad Request`.
5. **CSV Formula Injection:** Leading spreadsheet characters (`=`, `+`, `-`, `@`) sanitized with single quotes.
